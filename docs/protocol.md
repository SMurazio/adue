# Protocol

The protocol is binary and versioned. It is intentionally small so packet behavior is easy to inspect.

## Movement Model

Movement is tile-stepped (the model landed at v9; the held-direction `MoveIntent` that replaced the per-step `MoveStep` stream landed at v15, S43; the wire has since advanced — current shipped is **v40**, keep in sync with `ProtocolCodec.Version`). Input is state, not events: the client sends `MoveIntent` with an input sequence, a `Moving` flag, and one 8-way `Direction` (`N`, `NE`, `E`, `SE`, `S`, `SW`, `W`, `NW`) — on change (keydown / keyup / direction change) plus a low-rate keepalive (~500 ms), not once per step. The server holds the latest intent per session and, each tick, for every session whose intent is `Moving` and whose step cooldown has elapsed, attempts exactly one tile step in `Direction` — validating cooldown, world bounds, and blocked tiles exactly as before. A blocked target keeps the intent (the entity steps once unblocked or redirected). `Moving=false` halts. A `Moving` session that goes silent (no intent for ~1 s) is force-stopped server-side. Stale intents (`Sequence <= lastSeq`) are ignored. There is still no client prediction; the server paces steps on its own cooldown, so step cadence no longer depends on client send timing. Rationale: [movement-input-model.md](movement-input-model.md).

Positions in `LoginResult`, `EntitySpawn`, and `WorldSnapshot` are integer tile coordinates. Entity snapshots also carry facing. Clients tween between confirmed tile centers; there is no client-side prediction. Rationale: [networking-design-plan.md](networking-design-plan.md) section 5a.

Step cadence is **per-entity** (S51, v16). Each `WorldEntity` carries a `SpeedMultiplier` (default `1.0`); the server derives an effective step cooldown (base cooldown ÷ multiplier, clamped to the configured min/max) and the tick loop paces that entity at its own effective cooldown rather than a single global one. Default `1.0` is byte-for-byte identical to the previous single-cadence behaviour. The cooldown is advertised on `EntitySpawn` and re-advertised via `MovementSpeedChanged` when it changes; the client tweens each entity at its advertised cadence, falling back to the `ServerHello` global when an entity carries no explicit value. This is still server-authoritative and prediction-free — only the cadence varies. The admin-gated `/speed <multiplier>` dev command sets the caller's own multiplier to exercise it end-to-end (item/buff-driven speed is a separate follow-up).

- `uint16` message type
- message-specific payload

The transport is LiteNetLib:

- reliable ordered delivery for login, chat, entity spawn/despawn metadata, and `MovementMode`
- **unreliable + redundant** delivery for the movement input channels — `MoveInput` (held intent, NET1) and `StepCommitBatch` (UO commits, NET2): each packet repeats a sliding window of recent sequenced entries, so reliability comes from *redundancy, not retransmission* — a dropped packet recovers from the next packet's window instead of a head-of-line-blocking reliable retransmit batch (the old `MoveIntent` / per-step `StepCommitRequest` sends, now superseded)
- unreliable delivery for compact world snapshots
- sequenced delivery for snapshot acknowledgements

World snapshots should fit in a single UDP packet for the current channel target. Entity identity is sent separately with `EntitySpawn`; the hot `WorldSnapshot` path carries only a channel-local network id, tile coordinates, and facing. Each snapshot has a per-client sequence number, and clients send `SnapshotAck` with the latest sequence they received. The ack is harmless under full snapshots today and exists to unlock delta-against-acked-baseline snapshots later.

Between full heartbeat snapshots, `WorldSnapshot` may be incomplete (`isComplete=false`) and contain only visible entities whose tile/facing changed for that recipient. Clients merge incomplete snapshots into their current visible set. Full heartbeat snapshots remain self-contained.

`EntityDespawn` tells a client that an entity left its current area of interest. Clients should remove the rendered object/list row but may keep cached metadata for faster re-entry. The server first applies per-client area-of-interest selection, currently radius based with a visible-entity cap. Unchanged snapshots are skipped except for a low-rate heartbeat. The development target is roughly 120-150 **visible** players per channel — a conservative floor, not a measured ceiling: the capacity ladder (`capacity-ladder-study.md`, S40) shows server CPU is far from the bound and the real limiters are per-client bandwidth and the AOI scan at high *visible* density.

## Client Messages

- `ClientHello`: optional client name/diagnostics.
- `LoginRequest`: dev account name and display name.
- `MoveIntent`: input sequence, a `Moving` flag, and an 8-way direction (held-direction intent; the server steps the entity from this at its own cooldown cadence). `Moving=false` = stopped (direction ignored). *(v23, NET1: the WIRE delivery of held intent is now `MoveInput` below — `MoveIntent` stays DEFINED but is no longer the send path.)*
- `MoveInput` (v23, NET1): the **redundant-unreliable** held-intent channel that replaces the reliable `MoveIntent` send. Each packet carries the FULL current intent (`HeadSeq` / `Moving` / `Direction`) — so a lost packet is superseded by the next — PLUS a sliding `Window` of the last few prior inputs as deltas `{SeqDelta, Moving, Direction}` off `HeadSeq` (entry seq = `HeadSeq − SeqDelta`), so an intermediate state change dropped on the wire is recovered from a later packet. Sent unreliable at a fixed rate (~20 Hz while moving plus a short `Moving=false` tail after stop). The server dedupes by sequence (walks head+window, applies each seq > `LastMoveSeq` through the EXISTING held-intent path) — no head-of-line stall, no retransmit bunching. Sequence shares the `MoveIntent`/commit cursor. (Server still held-paced; authored-tick replay is a later stage.)
- `MovementMode` (v22, UO1): a one-bit `ClientDriven` declaration — `true` enters UoClientDriven (the client predicts + banks tiles locally and drives its own movement via the commit stream, so the server STOPS auto-pacing this entity from the held intent), `false` reverts to server-paced. Reliable-ordered; re-sent on (re)login/respawn so a lost flag can't silently double-step.
- `StepCommitRequest` (v21, S103): input `Sequence` plus an 8-way `Direction` — a client→server request to FINISH a near-complete step on key-release instead of snapping back. *(v24, NET2: the WIRE delivery of commits is now `StepCommitBatch` below — `StepCommitRequest` stays DEFINED and its server handler is intact, but the client no longer sends it.)* In model B (cosmetic lead), when the avatar's render has glided past the client's commit threshold (F6, default ~0.7) onto the next (walkable) tile at release, the client sends this and keeps the render gliding to that tile; the server validates it as a single server-authoritative step in `Direction` with the SAME walkability gate as `MoveIntent` PLUS an **anti-cheat floor**: the entity must be at least `CommitAcceptFraction` (server const, `0.5`) of its cooldown into the current step. On accept the step is scheduled from its NOMINAL end (the early finish CONSUMES the current step's remaining cooldown — it gains no time), so the average step rate can never exceed the normal cadence (no speedhack). Reliable-ordered; `Sequence` shares the `MoveIntent` cursor (stale `Sequence <= lastSeq` ignored, and a commit never resurrects a stopped intent). **There is no dedicated reply** — the result is observed via the normal snapshot stream: the confirmed tile advancing to the requested tile = accepted; staying put = rejected (the client then snaps the render back). Sub-threshold releases use the existing snap/soft-settle release behaviour; the commit is an additional release path, not a replacement.
- `StepCommitBatch` (v24, NET2; v25, NET3): the **redundant-unreliable** commit channel that replaces the per-step reliable `StepCommitRequest` send (used by UoClientDriven's per-step stream AND the model-B release commit). Each packet carries the NEWEST committed step (`HeadSeq` / `HeadTick` / `Direction`) PLUS a sliding `Window` of the last few prior committed steps as deltas `{SeqDelta, TickDelta, Direction}` off the head (a commit has no `Moving` flag — it is always a step; entry seq = `HeadSeq − SeqDelta`, entry authored tick = `HeadTick − TickDelta`). `HeadTick`/`TickDelta` (v25, NET3) carry each commit's **authored tick** — the integer server tick the client's predictor banked that step on (the SAME tick the prediction advanced on, not a separately-sampled clock). The server reconstructs each commit's (sequence, authored tick), dedupes by the shared move cursor, and applies each FRESH commit at its **authored tick** (`TryCommitStepAuthored`): the cooldown/eligibility SCHEDULE is keyed on authored time, not the receive tick. This is the loss-desync fix — under loss a dropped commit is recovered from a later packet's window but arrives BUNDLED with the next; the old receive-time gate applied both at one tick and rejected the second "too early", but keying on authored ticks lets `C2`(authored T+3) advance the schedule so `C3`(authored T+6) is accepted. Anti-cheat is preserved on authored ticks: the authored tick is clamped to `[serverTick − pastWindow, serverTick + futureLead]` and a commit's authored tick must be ≥ the prior accepted commit's authored tick + the step cooldown (the SPACING gate — a client cannot claim steps closer than cadence). Forward replay only; a genuine reorder (authored < last accepted) is dropped (full reorder rollback is deferred). Sequence shares the `MoveIntent`/`MoveInput` cursor.
- `ChatSend`: text chat for the current zone. Slash-prefixed text is interpreted as a server command after authentication.
- `SnapshotAck`: latest `WorldSnapshot` sequence received by the client.
- `InteractRequest`: network id of the target entity (generic verb; harvest is the first resolution). The server validates authentication, AOI-visibility, and ≤1-tile adjacency before resolving.
- `AdminSetStat` (v?, COMBAT-S1): admin-gated client→server "set my local player's current vital" verb (dev-set window). Same admin role gate as the other admin commands.
- `Attack` / `AttackMessage` (v28, COMBAT-S2B; v29, FREEAIM; v30, SWING-COMMIT-FIX): client→server attack action on its OWN dedup cursor (never movement's). Carries the attack sequence + attack kind (v28), a quantized continuous AIM ANGLE — the player→cursor world bearing the server resolves a geometric sector against (v29, `ushort` 0..65535 → [0,2π)), and an AUTHORED TICK — the integer server tick the client stamped the swing on, so the server roots the attacker's movement at the SAME logical tick the predictor did (v30, mirroring the NET3 step commit; kills the swing-then-move rubberband under latency). Reliable-ordered.
- `LootAction` / `LootActionMessage` (v35, LOOT P4c): client→server loot-window verb on a corpse the player has OPEN — `TakeItem` (one stack by template key), `LootAll`, or `Close`. (OPENING the window reuses the existing `InteractRequest` on the corpse.) Reliable-ordered — a dropped take/close must not be lost.
- `AdminSetTuning` (v17, S60): `string key`, `double value` — an admin-only request to set a live server tuning param. Reliable-ordered. The server **requires the session to be Admin** (the same role gate as `/speed` and `/metrics`); a non-admin request is **ignored** (logged, no reply, no disconnect). The key is looked up in a server-side registry that clamps/validates and applies it to a mutable runtime tuning holder (`ServerTuning`, seeded from `ServerOptions` at startup); an unknown/invalid key is ignored + logged. Starter keys: `move.stepCooldownMs` (global base step cooldown, clamped to `[50, 5000]` ms — the same bound `ServerOptions` validates) and `aoi.interestRadius` (clamped to `[1, 512]` tiles). *(The `move.turnDelayMs` key was removed in v20 (S98) along with turn-then-move.)* The change takes effect on the next AOI pass / step; nothing is persisted (the panel finds values, defaults are baked in afterwards). There is no echo message in v1 — the client shows the value it sent; the server logs the post-clamp authoritative value.

## Server Messages

- `ServerHello`: server name, protocol version, tick rate, authoritative step cooldown in milliseconds, and server interest radius in tiles. *(v20, S98: the `turnDelayMs` field was removed — turn-then-move/turn-delay is gone, so a direction change steps immediately in the new direction with facing set on the step; there is no separate turn beat or turn-timing for the predictor to mirror.)*
- `LoginResult`: accepted/rejected, character id, display name, assigned role, spawn tile, reason.
- `ZoneInfo`: zone id, width, height, and a **procedural-terrain descriptor** — `int32 seed`, `int32 genVersion`, and `uint64 contentHash`. Static terrain is content, not state: rather than shipping the blocked-tile list, the server ships the seed and the client regenerates the identical map locally via the shared deterministic `TerrainGenerator` (`(width, height, seed, genVersion) -> blocked tiles`). The client compares its locally-computed hash to `contentHash` as a drift/tamper check and logs loudly on mismatch; the server remains authoritative for movement. Login terrain cost is constant regardless of map size. `genVersion` lets the generator algorithm change later without a silent mismatch.
- `EntitySpawn`: durable visible-entity metadata: network id, character id, kind, display name, initial tile, facing, and the entity's **effective step cooldown in milliseconds** (`uint16`, S51) so a viewer knows the entity's movement cadence the moment it sees it. The cooldown is the server's clamped per-entity value (base cooldown ÷ the entity's speed multiplier, clamped to the configured min/max), tick-quantised so it round-trips to the same tick count the client re-derives. Default speed (multiplier 1.0) yields the global cadence.
- `MovementSpeedChanged`: reliable-ordered notice (`uint32 networkId`, `uint16 stepCooldownMs`, S51) that an entity's effective step cadence changed mid-session (a speed buff/slow/mount applied or removed; the `/speed` dev command). Sent to every viewer whose area of interest currently includes the entity. Movement speed is kept **off** the hot `WorldSnapshot` path — cadence changes are rare relative to position updates — and rides this reliable message instead, like spawn/despawn. The client retunes that entity's tween cadence to the new cooldown (still no prediction; just confirmed-step tweening at the right speed).
- `EntityDespawn`: server tick plus network id for an entity that left the client's current area of interest.
- `WorldSnapshot`: server tick, per-client snapshot sequence, and compact visible entity state. Each entity state is `ushort networkId`, `int16 tileX`, `int16 tileY`, `byte facing`, `byte depleted` (the resource-node availability flag — false for players and all non-resource entities).
- `InteractResult`: success flag plus a short reason code (`too_far`, `depleted`, `not_resource`, `no_target`, `inventory_full`, `rate_limited`, …; empty on success). Sent to the requesting owner only.
- `InventoryUpdate`: owner-only private inventory delta — the changed stacks, each carrying the new authoritative total quantity (0 = emptied). Never AOI-replicated.
- `ChatBroadcast`: sender plus text.
- `PlayerStats` (v?, COMBAT-S1): server→owner replication of the local player's vitals (HP / mana / stamina, current + max). Owner-only.
- `CombatTuning` / `CombatTuningMessage` (v31, COMBAT-TUNING): server→client replication of the live combat feel-knobs (attack cooldown ms, swing-root ms, sector half-angle deg / radius tiles, damage). Sent on login + on every `combat.*` tuning change so the client's wedge / predictor / cooldown-viz match the server's authoritative resolution.
- `DamageEvent` / `DamageEventMessage` (v32, COMBAT-QOL): server→client cosmetic damage event (victim network id + damage amount + new health), AOI-gated to the victim's viewers, so the client floats a "-N" number over the entity. Presentation only — authoritative HP still rides the snapshot; sent UNRELIABLE (a dropped number is harmless).
- `MonsterTuning` / `MonsterTuningMessage` (v33; DATA-DRIVEN at v40, LIVING-ENEMIES P2-POLISH): server→client replication of the per-monster-TYPE tuning (one entry per named template — slime today). Each type carries a stable `Id`, a `DisplayName`, and a GENERIC list of tunable fields — each `{Key, Label, Value, Min, Max, IsInteger}` — built once from the server's `MonsterTypeRegistry` tunable descriptors. The F1 "Monster" tab renders one labelled row per field and sends `AdminSetTuning("<typeId>.<Key>", value)` on Apply, so a new server-side knob (e.g. `hopDistance`, `hopHeight`, `hopAirborneMs`) appears in the tab with no client or protocol change. Sent on login + on every per-type tuning change.
- `SpawnerMarker` / `SpawnerMarkerMessage` (v34, LIVING-ENEMIES P3): server→viewer replication of a SPAWNER's red-tile marker — the PERSISTENT leash/respawn anchor, keyed by a stable spawner id (not the monster's network id, which changes on death/respawn) with an `Active` flag (true on AOI-entry, false on AOI-exit). Replaces the former per-monster `MonsterHome`; the marker STAYS PUT while a monster dies and respawns. Reliable.
- `CorpseContents` / `CorpseContentsMessage` (v35, LOOT P4c): server→owner replication of an OPEN corpse's contents — the rolled stacks (template key + quantity + rarity tier) the loot window lists, rarity-coloured. Sent eligibility-gated when the player opens a corpse and re-sent after each take/loot-all; `Open=false` tells the client to CLOSE the window. Owner-only + reliable-ordered (corpse loot never AOI-replicates, like `InventoryUpdate`).
- `ServerError`: code and message.

## Rules

- The server may reject invalid protocol versions.
- Movement steps are validated server-side against cooldown, bounds, and blocked tiles.
- Snapshot tile coordinates are server-owned truth.
- Snapshot acknowledgements are advisory; full snapshots remain self-contained until delta snapshots are explicitly added.
- Snapshot chunks may be split when the packet budget requires it; clients should assemble chunks for the same tick before treating a snapshot as complete.
- Chat text is length-limited by the codec and should be sanitized before any rich client renders it.
