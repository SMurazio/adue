# N (S-class when started) — Phase B2: client prediction + reconcile of the action (the netcode CRUX)

The high-risk phase. Full rigor: **measure/repro first**, headless determinism test under loss/latency, independent review, green gate, then the human live feel-test. Per `docs/movement-actions-design.md` §2. Builds on B1 (`6870171`, the wire + replicated vertical, server-executed, reviewed SHIP).

## Tick-alignment model — DECIDED (measure-first, `6881c71`): MODEL A, no estimator.
The measurement probe `Measure_PredictionLeadAlongTheArc_UnderLatency` (off the real executor) showed: with the client predicting on its LOCAL clock from trigger and the server running the same deterministic action from receipt (~RTT later, force-included each tick), the client's predicted position LEADS the server's along the SAME arc by exactly `D` units (D = one-way latency in ticks; ~1 tile/50ms for the seed jump), and BOTH sides land at the IDENTICAL spot regardless of latency — the lead is purely TEMPORAL, so under no-loss there is ZERO correction (the determinism contract, exactly like movement prediction). So `EstimateServerTick` is NOT needed (it would only zero an invisible temporal lead). **Hard implementation constraint the measurement pins: the reconcile must RENDER the predicted-ahead action position and correct only genuine mispredicts (loss/rejection) — it must NEVER re-base the render to the lagging server position, or the avatar snaps back ~D tiles per snapshot.**

## Implementation plan (Model A)
- **Shared stepping primitive:** extract the per-tick action advance (Trajectory → shared collision → XY; BallisticArc → Z) so the CLIENT predictor and the server `ServerActionExecutor` call BYTE-IDENTICAL code (determinism). Today the stepping lives in `ServerActionExecutor.Step` — factor the math into `Mmo.Shared` so the client reuses it.
- **Client predicts:** on a skill/trigger, mint actionSeq, snapshot `ActionContext` (origin = current predicted pos, heading, speed), start a LOCAL action instance, advance it by WHOLE TICKS on the client's local clock (accumulate frame dt), drive the predicted XY+Z each tick; SUPPRESS normal movement prediction while the action owns the entity (mirror the server's `HandleMoveIntent` suppression). Send the `ActionIntent` (B1's `SendAction` already exists).
- **Reconcile keeps the lead:** the action's per-tick predicted positions go in the predictor buffer as action entries `{actionSeq, tickInAction, ctx}`; on a snapshot, re-base to the server's (force-included) action position, drop acked, replay the unacked action ticks via the shared primitive → predicted = server action pos + the client's still-unacked action ticks (the lead). No-loss ⇒ replay == prediction ⇒ silent. (Resolve the action-tick ACK mechanism — the per-frame move inputSeq the server keeps ACKing while suppressed, vs a dedicated action-tick counter — during impl; surface if the frame/tick correlation is too loose.)
- **Carry-forward #1 (Z double-count) lands here:** while predicting, the LOCAL player must render its PREDICTED Z, NOT the replicated `VerticalOffset` from the snapshot (B1 routed the local body through the confirmed Z; B2 switches the local player to predicted Z for the action's duration — one Z source, no double-count).
- **One-at-a-time on the client** (decline a 2nd local action while one is active, §2.8) so the spam case never mispredicts.
- **Server can-act already validates** (B1 + the rooted-jump gate); when B2 consumes `authoredTick`, window-clamp it like the swing path (or keep receipt-anchor — Model A doesn't need the authored tick at all, so likely leave `AuthoredTick:0`).
- **The gate (the determinism test the 3 misses lacked):** a headless harness running the client-predicted action + the server action under simulated LOSS + LATENCY, asserting byte-identical paths (XY+Z) with no loss (zero correction) and BOUNDED, converging corrections under loss — plus a rejected-action snap and a spammed-second-trigger (one-at-a-time) test. Independent review + human live feel-test.
- Extend `ContinuousPredictor`'s buffer to carry action entries (`{ActionId, ctx, tickInAction}` vs `{dir, dt}`); replay dispatches `Trajectory` for action ticks, the integrator for move ticks (design §2.4).
- Enforce **one-at-a-time on the client** (decline a 2nd local action) so the common spam case never mispredicts (§2.8).
- Server can-act already validates (B1); when B2 consumes `authoredTick`, window-clamp it like the swing path.
